+++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++

	Known Bugs / Side Effects
	
+++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++

## Bug
    VisISetClass: The red border is drawn outside the bounds 
    --> If only the border is covered by a menu, it is not redrawn 
    --> Adjust the bounds and the bitmap text so that the borders
    are within the bounds

## Bug
    When editing a mouse pointer, all colors are available. 
    MSG_DB_VIEWER_POINTER_IMAGE_ENTER_PTR_MODE actually disables the color dialogs, but 
    because EnableEditing() is called later, the dialogs are re-enabled.
    --> We should take a close look at the sequence and see if we can adjust it
    --> We need to give the toolbar some more thought
    --> It’s not worth the effort right now

## Not ideal, but probably impossible or very difficult to fix:
    After a restart, the selection is lost if the selection tool is open
    Cause: DETACH_UI calls KILL_ANTS (<- clears the selection). However, this is
    necessary to kill the timer.
    --> KILL_ANTS would have to distinguish between “timer only” and
    “timer + selection,” and restart the timer upon reboot
    --> Not worth the effort!

## Not ideal, but probably not/only difficult to fix:
    All dialogs started with UserDoDialog() disappear
    after a system reboot.
    Same goes for all MessageBox, MessageBoxOptr, etc.
	The only ones I can reasonably restore (with acceptable effort) are
    CropImageDialog and AnimatISetDialog

## Not ideal, but probably impossible or very difficult to fix:
    All dialog boxes that contain (at least) one VisListContentClass object as
    a replacement for a DynamicList must be closed upon restart
    (unfortunately, closing them on shutdown doesn’t work).
    Reason: The VisListContentClass would have to be reinitialized
    upon restart, which is very time-consuming and, at least for the SortIconDialog, also depends on the
    current document or CurrenISet.
    I’ve decided it’s not worth the effort.

## Not ideal, but not—or only very difficult—to solve:
    Floodfill cannot use a fill grid (25%, 50%, etc.) because this
    causes neighboring pixels to be skipped,
    which the algorithm then does not recognize as “completed,” so that
    only a few pixels are “processed” recursively and the algorithm
    does not terminate.
